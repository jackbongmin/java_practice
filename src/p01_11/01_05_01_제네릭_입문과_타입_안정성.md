# 5일차 1교시 실습 — 제네릭 입문과 타입 안정성

## 이번 시간에 할 일

- 제네릭 코드에는 형 변환이 왜 없는지, "생략"이 아니라 "컴파일러가 타입을 안다"로 설명해 봅니다.
- 잘못된 타입을 넣는 실수가 실행 중이 아니라 컴파일 시점에 걸리는 것을 직접 만들어 봅니다.

## 실습 파일

- `chapter11/Box.java`
- `chapter11/GenericOperatorExample.java`

## 미션

### 1-1. 먼저 예측하고 실행한다
`GenericOperatorExample`을 실행하기 전에 출력 두 줄을 예측해 적고, 실행해 비교합니다. 예측과 결과가 다르면 어디를 잘못 읽었는지 표시합니다.

### 1-2. T가 앉는 세 자리
`Box.java`에서 타입 파라미터 `T`가 나타나는 세 자리(필드·매개변수·반환)를 찾아 표시합니다. `Box<String>`으로 쓸 때 이 세 자리가 각각 무엇이 되는지 적습니다.

### 1-3. 잘못된 타입은 컴파일이 막는다
`GenericOperatorExample`에 다음 줄을 추가합니다.

```java
stringBox.setItem(42);   // String 상자에 int 를 넣으면?
```

**실행하지 말고** 컴파일만 해서 오류 메시지를 원문 그대로 기록한 뒤 지웁니다.

### 1-4. raw type으로 되돌리면 형 변환이 살아난다
`Box.java`는 그대로 두고, `GenericOperatorExample`에서 `Box<String> stringBox = new Box<>();` 를 `Box stringBox = new Box();` (raw type)로 바꿉니다. `String greeting = stringBox.getItem();` 줄이 왜 깨지는지 오류를 기록하고, `(String)` 캐스팅을 넣어 통과시킨 뒤 원래대로 되돌립니다.

### 1-5. 실패가 드러나는 시점
1-4의 raw type 상태에서 `stringBox.setItem(42);` 를 다시 넣으면 컴파일이 통과하는지 확인합니다. 통과한다면 이 코드는 **언제** 실패하는지 한 문장으로 적습니다. 확인 후 모두 되돌립니다.

## 스스로 점검

- 1-3(제네릭)과 1-5(raw type)의 차이를 "실패가 드러나는 시점"으로 설명할 수 있다.
- 제네릭 코드에 형 변환이 없는 이유를 "컴파일러가 타입을 안다"로 말할 수 있다.
- `new Box<>()`의 `<>`가 무엇을 생략한 표기인지 안다.

## 막혔을 때

- 클래스명과 파일명이 대소문자까지 같은지 확인합니다.
- 파일 맨 위 `package chapter11;` 과 실제 폴더 경로가 맞는지 확인합니다.
- "컴파일만" 하라는 미션은 실행하지 말고 오류 메시지 자체를 관찰하는 것이 목적입니다.
